## Design and changes

Correctness, measured efficiency and operator judgment have separate evidence.
Small modules own admission permits, query-task lifetime, render-budget policy,
viewer health and source presentation. Interfaces expose the required operations;
regression tests exercise caller-visible behavior rather than private structure.

- BP-01's original backend/frontend pair was built from a clean `c15bd42` archive,
  revision-checked and isolated-smoked. The follow-up has a matching three-service
  set because downstream cancellation requires the updated Intelligence service.
- BP-02 authorizes and acquires a common Linux worker permit before side effects,
  with capacity one and queue capacity zero. Busy requests receive actionable 429
  responses. Dead workers release kernel-owned permits; completion, disconnect,
  error and timeout own explicit cleanup. Browser callbacks cannot write a late
  result into another dossier. [Contract and limits](../operations/model-admission.md).
- Analysis shows honest progress, explicit cancellation and safe error messages.
  Dossier reload failures are recoverable; source URLs have visible keyboard focus;
  small metadata text has improved contrast. No fabricated countdown or agent stage.
- Native rendering uses public `scene.postRender` events. The historical coverage
  counter was reproduced but did not count actual frames. The corrected baseline
  already achieved about 60 FPS; no unsupported speedup is claimed.
- Two viewer lifetime defects were fixed: retained terrain-cache context buffers
  and credit stylesheets. The private Cesium compatibility seam is pinned to
  1.142.0 and must be requalified on upgrades. A failed graphics context now stops
  rendering and exposes a controlled map reload with layer state retained.

## Native browser memory: unresolved acceptance boundary

The retained JS/DOM criteria passed, but the broader "no continuing memory rise"
criterion is **OPEN**. Chrome's browser process grew from a 260.9 MiB median in
minutes 10–15 to 409.1 MiB in minutes 55–60 (+148.2 MiB, about 3.26 MiB/min).
The GPU-process RSS warm delta was +2.0 MiB; the app-renderer median was lower in
the late window. RSS is a separate native/shared-memory observation, not JS heap.

Controls narrowed the issue without a speculative application patch:

- 300 large HTTP/JSON responses, with/without request interception and history
  navigation, produced only about 0.8–6.0 MiB browser RSS growth.
- 150 plain native WebGL contexts, with/without explicit context loss, produced
  about 9.7–9.8 MiB growth.
- Cesium worker blobs remained constant at 38 URLs / 17,348,483 bytes over 20 map
  remounts. The browser process still grew by about 28 MiB; simulated pressure
  did not reclaim it. The initial diagnostic fixture returned before its final
  canvas existed; that harness failure is preserved and corrected by awaiting it.
- A minimal Cesium viewer using the same distribution, without ODIN, reproduced
  about 31 MiB growth over 25 mounts both with and without Playwright routing.
  Without imagery it still grew about 21 MiB. Closing that page returned the
  browser process near its initial level. Explicit WebGL loss did not improve it.

This isolates a reproducible Cesium/browser lifecycle interaction, not its exact
native allocation owner or a proven upstream fix. It does not exonerate every
application path. Do not replace this open gate with the narrower 60-minute
JS/DOM PASS or roll out a speculative worker/context workaround.

Raw controls and process samples are in `evidence/*memory-control*`,
`cesium-explicit-context-release*`, `native-worker-pressure-control`, and
`host-memory-final-summary.json` under the external evidence root. Next technical
cursor: reproduce the minimal case with native allocation profiling or an
independently isolated browser/engine version; qualify a measured fix before
claiming the full long-running memory gate. Current app images remain unchanged.
